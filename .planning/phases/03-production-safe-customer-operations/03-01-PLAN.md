# Plan 03-01 — Durable Authorized API Foundation

<objective>
Prove the Phase 3 durable authorized architecture end to end with one authenticated tracer: a Cloudflare D1 database, a Worker API that verifies Cloudflare Access JWTs per request, stateless operator identity, authoritative server-side enforcement of the shared pure rules, a purpose-built endpoint surface, and immutable audit entries committed in the same D1 transaction as every mutation.

Purpose: Establish the durable storage, authorization, identity, and audit foundation that every later archive, audit-UI, migration, and hardening plan builds on.
Output: D1 schema and migrations, JWT verification and identity modules, the purpose-built Worker API, the immutable audit writer, the archived lifecycle status with schema v4, and Worker integration tests proving the authenticated tracer and permission failures.

<acceptance_criteria>
- SAFE-03, SAFE-04, SAFE-05, and the server half of SAFE-06 work through the real Worker, D1, shared rules, and JWT boundary.
- A request without a valid Cf-Access-Jwt-Assertion header is rejected with 401 before any route logic; a valid token yields the operator identity.
- Every mutation commits its rows and one immutable audit entry in the same D1 transaction; audit rows are never editable or deletable.
- The purpose-built endpoint surface maps one-to-one to console workflows; there is no generic CRUD and no DELETE /api/customers/:id.
- The Worker enforces the shared pure rules authoritatively; a tampered client cannot bypass validation.
- Worker integration tests and the full regression gate pass before this plan may hand off.
</acceptance_criteria>
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser to Worker API | Untrusted Cf-Access-Jwt-Assertion headers and request bodies cross into the API. |
| Worker to D1 | Mutation rows and audit rows cross into the durable database. |
| shared pure rules to D1 writes | The authoritative validation result determines what may be committed. |

## STRIDE Threat Register (ASVS Level 1)

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Spoofing | access-jwt verification | high | mitigate | Verify RS256 signature against the cached Access JWKS and check iss, aud, exp, and nbf; missing header → 401 before any route logic (D-03, ASVS V2/V3). |
| T-03-02 | Tampering | mutation routes | high | mitigate | Every mutation enforces the shared pure rules server-side and commits rows plus the audit entry in one env.DB.batch() transaction (D-07, ASVS V5). |
| T-03-03 | Tampering | archive command | high | mitigate | Archive flips the lifecycle status only and never touches dependent tables; double-archive returns 409 (D-05, SAFE-01). |
| T-03-04 | Repudiation | audit writer | high | mitigate | Audit entries commit in the same D1 transaction as mutations, carry the verified operator identity, and are never updated or deleted (D-06, SAFE-05). |
| T-03-05 | Tampering | ledger/usage rows | high | mitigate | Append-only semantics and derived balances only; no stored balance counter exists (D-12). |
| T-03-06 | Information disclosure | D1 data | medium | mitigate | Every /api/* request requires a verified Access JWT; no public read endpoints; baseline security headers retained (SAFE-04). |
| T-03-07 | Denial of service | JWKS fetch / large payloads | low | mitigate | Cache the JWKS with a short TTL; validate DTO shapes and whole-token ranges before any database work. |
</threat_model>
