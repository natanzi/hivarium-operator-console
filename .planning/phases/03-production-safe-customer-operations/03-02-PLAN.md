# Plan 03-02 — Server-Backed Console, Archive and Audit UI

<objective>
Point the existing console at the authoritative Worker API while preserving the UI: an async repository boundary, honest loading/error states, operator identity display, non-destructive archive replacing delete, and a read-only operator audit trail inside the existing Activity tab.

Purpose: Turn the durable authorized foundation from 03-01 into the operator-facing console without redesigning it, and prove SAFE-01 and SAFE-05 through the real UI.
Output: Async ApiRepository and LocalStorageRepository, async-aware pages with skeleton/error states, the archive workflow (confirmation, filter, banner, read-only profile), the Operator audit trail, identity display, and API-backed E2E journeys.

<acceptance_criteria>
- SAFE-01, SAFE-05, and the client half of SAFE-06 work through the real SPA, async repository, Worker API, and D1 boundary.
- The console UI is preserved: same four tabs, list, catalog, confirmations, copy, and responsive behavior; only the data layer, archive action, audit section, and identity line change.
- Archive replaces delete: archived customers leave the default list, appear under the Archived filter, and their profile is read-only with a banner while every dependent record remains readable.
- The Activity tab shows the read-only Operator audit trail newest first for every covered mutation.
- The sidebar shows Signed in as {email}; a 401 renders the sign-in-required state.
- Component tests, API-backed E2E, and the full regression gate pass before this plan may hand off.
</acceptance_criteria>
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| SPA to Worker API | Untrusted operator input and the Cf-Access-Jwt-Assertion header cross into the API. |
| Worker API responses to SPA state | Error codes and DTOs drive toasts, skeletons, and the sign-in-required state. |
| audit rows to audit trail UI | Server-written immutable rows are rendered read-only. |

## STRIDE Threat Register (ASVS Level 1)

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-08 | Tampering | archive action | high | mitigate | Archive calls the purpose-built endpoint; the Worker enforces retention semantics; the UI never deletes locally (D-05, SAFE-01). |
| T-03-09 | Spoofing | identity display | high | mitigate | Identity comes only from GET /api/me backed by the verified JWT; a 401 renders the sign-in-required state (D-04). |
| T-03-10 | Repudiation | audit trail UI | medium | mitigate | The trail renders server-written immutable rows newest first; no edit/delete/export action exists (D-06, SAFE-05). |
| T-03-11 | Information disclosure | archived profiles | medium | mitigate | Archived profiles remain readable only to verified operators; every API read requires a valid Access JWT (SAFE-04). |
| T-03-12 | Denial of service | async retry storms | low | mitigate | Retry re-runs the same read; mutation failures retain entered values and never auto-retry writes. |
</threat_model>
